I found and confirmed a concrete, reproducible defect — **FINDING 1** — by building the diagnostic and running a controlled experiment.

The flaky failure in `TestRaft_ProtocolVersion_Upgrade_2_3` is caused by the test helper `cluster.EnsureSamePeers` (`testing.go:691`). It snapshots the reference peer set **once** (`peerSet := c.getConfiguration(c.rafts[0])`) and never refreshes it, while `otherSet` is re-read on every poll. If `c.rafts[0]` hasn't yet applied the just-committed configuration entry at that instant, `peerSet` stays at the old value forever, the comparison can never become equal, and the helper fails after its ~5 s deadline — even though the cluster is fully consistent.

Evidence (all in-memory, no sockets):

- Faithful copy of the test using the real helper: `go test -count=20 -run '^TestAuditUpgrade23StallDump$' .` → **6/20 failed** (`peer mismatch after timeout: {2 voters} vs {3 voters}`), logs in `work/.runtime/audit_stall2.log`.
- Same scenario but re-reading the peer set on each poll: `go test -count=20 -run '^TestAuditUpgrade23RefreshPeers$' .` → **0/20 failed** (`work/.runtime/audit_refresh.log`).
- A goroutine dump captured exactly when the helper gives up (`work/.runtime/stall_dump.txt`) shows all three nodes already at `lastIdx=3, committedIdx=3, latestCfg={3 voters}` — i.e. the cluster had converged, so my earlier "a node is stuck" hypothesis was wrong; the assertion was stale.

Necessary condition: a config change commits and another node applies it before `c.rafts[0]` does. This window is easy to hit right after `AddVoter` because a protocol-v2 leader's config entry produces no FSM log (`prepareLog` ignores `LogConfiguration` when `protocolVersion <= 2`), so the preceding `c.EnsureSame(t)` doesn't wait for it.

Impact: the shipped helper yields false "peer mismatch" failures (~30% here) on a healthy cluster — a test-harness defect, not a Raft safety/liveness violation.

I've kept two things honest in the report: this is a defect in the library's test-support file rather than the consensus core, and I cannot offline confirm whether the frozen-snapshot pattern is the injected mutation or a latent upstream flake (its shape matches what I recall of upstream). Next useful work is to look for any other caller/impact of the same helper and to continue probing for a consensus-level defect that isn't masked by this test artifact.
