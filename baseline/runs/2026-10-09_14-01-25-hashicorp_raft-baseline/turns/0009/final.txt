This turn I nailed down why the frozen-`peerSet` defect only surfaces in the upgrade test, which sharpens Finding 1 into a coherent, confirmed local defect.

The frozen reference in `EnsureSamePeers` is only stale if a node lags at the instant it is read, and the preceding `c.EnsureSame(t)` normally closes that window because a committed `LogConfiguration` entry is delivered to the FSM and `EnsureSame` waits for every node's FSM to see it. But `prepareLog` in `raft.go` only forwards `LogConfiguration` to the FSM when `r.protocolVersion > 2`. In `TestRaft_ProtocolVersion_Upgrade_2_3` the leader runs with `ProtocolVersion = 2`, so the config entry is not an FSM log, `EnsureSame` returns without waiting for it, and the window stays open for `EnsureSamePeers` to snapshot a stale 2-voter `peerSet`.

That prediction was testable, so I ran it: the tests that share the helper but use protocol-3 leaders — `TestRaft_JoinNode`, `TestRaft_JoinNode_ConfigStore`, `TestRaft_RemoveFollower_SplitCluster` — passed **60/60 combined runs** (`work/.runtime/join_c20.log`). Only the protocol-2 upgrade path flakes. So the defect is a genuine latent bug in the shipped `EnsureSamePeers` helper, with an observable trigger specific to the v2→v3 upgrade path.
