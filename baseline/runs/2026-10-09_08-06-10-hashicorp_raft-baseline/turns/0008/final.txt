Continuing the audit, I traced the panic class up to the network boundary and significantly sharpened its severity analysis.

**Key result this turn — F1–F3 are remotely triggerable by an unauthenticated sender (source-based + executed parts distinguished).**

Reading `net_transport.go`, I confirmed the sender need not be an authenticated cluster member:
- `listen()` accepts *every* incoming TCP connection (`conn, err := n.stream.Accept()` → `go n.handleConn(...)`).
- `handleConn`/`handleCommand` decode and enqueue the RPC with **no peer authentication and no membership check** (grepping for `auth`/`TLS`/peer-filtering finds only a generic doc comment).
- The only gate before `installSnapshot` is `checkRPCHeader`, which merely requires a sender-chosen `ProtocolVersion` in range (2..3).

So any host that can open a TCP connection to the Raft port can deliver the malformed `InstallSnapshot` (F1) — or the malformed `AppendEntries` of F2/F3 — and crash the node: a remote, unauthenticated denial-of-service. I kept the epistemics explicit in the report: the *executed* proof is the raft-layer panic via the in-memory transport; the transport-reachability part is *source-based*, because loopback TCP can't run in this sandbox (the network transport tests are among the blocked ones).

I also verified the net-transport decode layer itself is robust (`handleCommand` returns errors for unknown RPC types and decode failures), which localizes the defect to the raft-level handlers rather than the wire codec.
