**New this turn — Finding F2 (same class as F1): unknown `LogType` in `AppendEntries` panics on commit.**

`prepareLog` (`raft.go`) has `default: panic("unrecognized log type")`. That function is reached on the *follower* path too: `appendEntries` → `processLogs(idx, nil)` when the commit index advances. So a peer-supplied log entry with an unhandled `Type` (e.g. `99`) is stored, then panicked on at commit. No `recover()` exists in the RPC loop, so the node process aborts.

Reproduced with a focused test: `go test -run 'TestAudit_AppendEntries_UnknownLogTypePanics$' -v .` →
`REPRODUCED panic from appendEntries/processLogs: unrecognized log type: &raft.Log{... Type:0x63 ...}` (`audit/appendentries_unknown_type.log`).

**The class.** F1 and F2 show that several RPC-reachable paths feed unvalidated peer bytes into functions that panic, with no `recover()` anywhere in the RPC main loop (`processRPC` → `runFollower`/`run`). I listed the other likely members of the class without separately reproducing them: `processConfigurationLogEntry` (`DecodeConfiguration(entry.Data)`) and FSM config application (`fsm.go` `DecodeConfiguration(req.log.Data)`).

**Honest scope caveat (kept explicit):** both F1 and F2 require a peer to send a malformed message. Under the brief's pure crash-fault model (correct peers that only crash), a correct peer never produces this, so these are robustness/availability defects (one bad message from a buggy/Byzantine member crashes the receiver), not crash-fault-reachability safety defects. Both are inherited from upstream v1.7.3 — the tree is still byte-identical to the release, so no injected defect is claimed.
