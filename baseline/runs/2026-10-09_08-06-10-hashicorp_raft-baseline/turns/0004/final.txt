**Finding F1 — malformed `InstallSnapshot.Configuration` panics the receiving node.**

Expected behavior (basis): `installSnapshot` handles the analogous legacy `req.Peers` field gracefully — `decodePeers` returns an error, it's logged, and the RPC responds with an error (asserted by upstream's `TestRaft_InstallSnapshot_InvalidPeers`). The modern `Configuration` field is that field's replacement, so it should be handled the same way.

What actually happens: on the `req.SnapshotVersion > 0` branch, `installSnapshot` calls `DecodeConfiguration(req.Configuration)`, which is documented to **panic** on decode errors. There is no `recover()` anywhere in non-test code, and the panic occurs on the Raft main-loop goroutine (`processRPC` → `runFollower` → `run`), so a single malformed message aborts the node process.

Necessary conditions: `SnapshotVersion == 1`, an RPC-header `ProtocolVersion` inside the accepted range (so `checkRPCHeader` doesn't drop it first — this is a protocol gate, not input validation), a non-stale term, and a `Configuration` blob that isn't valid msgpack.

Reproduction (kept separate from the captured source, in `audit_panic_test.go`):
- Direct call, panic caught and logged: `go test -run 'TestAudit_InstallSnapshot_' -v .` → `REPRODUCED panic ... failed to decode configuration ...`, while the `Peers` control path returns an error.
- End-to-end over the transport/RPC loop, guarded so it doesn't break normal runs: `RAFT_AUDIT_CRASH=1 go test -run 'TestAudit_InstallSnapshot_NetworkCrash$' -v .` → process aborts with the panic stack through `installSnapshot → processRPC → runFollower → run`. Logs: `audit/install_snapshot_panic.log`, `audit/install_snapshot_network_crash.log`.

Honest scope/severity caveat (recorded in the report): this requires a peer to send a malformed message. Under the pure crash-fault model in the brief (correct peers that only crash), a correct peer never sends it, so F1 is a robustness/availability defect (one bad message from a buggy or malicious member crashes the receiver), not a crash-fault-reachability safety defect. Impact is local to the receiving node. It is inherited from upstream v1.7.3, not an injected mutation — the tree remains byte-identical to the release.
