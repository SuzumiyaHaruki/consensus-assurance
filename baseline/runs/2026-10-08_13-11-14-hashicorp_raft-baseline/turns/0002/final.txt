**Finding 1 widened**

The defect is `(*cluster).EnsureSamePeers` in `testing.go:692-715`: it captures `c.rafts[0]`'s configuration once and never refreshes it across the `CHECK`/`WAIT` retry loop. A single early read of a not-yet-converged node freezes the reference at the old configuration, so the comparison can never succeed and the test fails after `longstopTimeout`. Observed victims now: `TestRaft_ProtocolVersion_Upgrade_1_2`, `_2_3`, and `TestRaft_HasExistingState`. Enumerating callers, **10 tests** use the helper and are exposed (`RecoverCluster`, `HasExistingState`, `JoinNode`, `JoinNode_ConfigStore`, `RemoveFollower_SplitCluster`, `SnapshotRestore_PeerChange`, both `ProtocolVersion_Upgrade_*`, `LeaderID_Propagated`, `FollowerRemovalNoElection`).

**Root cause isolated and fix verified**

The diagnostic test (`audit_diag_test.go`) shows the never-refreshed capture goes stale in ~30% of runs while all three nodes live-report the new configuration within ~20 ms — i.e. the Raft implementation converges; the helper is at fault. I then ran the same scenario with the corrected logic (re-read the reference node each pass): **20/20 pass, 0 failures** (`audit/audit-fixed.log`), versus the ~25-50% failure rate of the unrefreshed helper. The fix is a one-line re-read in `EnsureSamePeers` and resolves it for all 10 callers.
