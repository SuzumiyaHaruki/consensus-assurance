Outcome: **C1 is confirmed as a defect in the shipped test helper `cluster.EnsureSamePeers` (`testing.go:691`), not a consensus-correctness defect.**

What I established:

- Root cause: `EnsureSamePeers` samples `rafts[0]`'s configuration **once** (`peerSet := c.getConfiguration(c.rafts[0])`) before its retry loop and never refreshes it, while every other raft's set is re-read each attempt. If `rafts[0]` is transiently behind when the helper is entered, the two can never compare equal, so it always fails after the 5s `longstopTimeout` even though the follower catches up immediately.
- Why `EnsureSame` doesn't mask it: `TestRaft_HasExistingState` applies no command entries, and the default `mockFSM` does not implement `ConfigurationStore` (only `MockFSMConfigStore` does — `testing.go:45,110`, `fsm.go:113-119`), so `EnsureSame`'s comparisons are vacuous and it returns instantly with no propagation barrier.
- Executed evidence: unmodified tree fails **18/100** (`go test -count=100 -run '^TestRaft_HasExistingState$' .`); with only `peerSet` refreshed inside the loop it passes **100/100**. Instrumented traces (`RAFT_DIAG=1`, scratch copy `work/diag/`) show the follower actually receives and applies the new entry promptly (`recvAppendEntries ... first=3 last=3` → `setLatestConfiguration index=3 nservers=3`), so the replication path is correct and only the helper's stale reference is at fault.
- Blast radius: 10 `EnsureSamePeers` call sites; those that apply commands first (JoinNode, RecoverCluster, LeaderID_Propagated) passed 30/30 — they're protected because `EnsureSame` then acts as a real barrier. Only `HasExistingState` exposes the race.

Unchanged: provenance still shows the graded module is byte-identical to upstream `v1.7.3` (no injected defect); the only "extra" differences are the two nested test-harness modules excluded from the parent module zip.
