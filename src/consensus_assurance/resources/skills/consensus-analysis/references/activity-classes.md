# Activity roles

The controller's activity_roles is the authoritative mapping. Core relationships and supporting mechanisms are neither execution stages nor a disjoint partition of code. Support is not lower importance: persistence, membership or client contracts can determine the core requirement. A question need not cover both core dimensions or every support mechanism.

Initial understanding covers consensus formation/advancement and context/authority transitions together. Explain their actual connection: which support remains eligible across which transition, who can consume it, and how pending work or prior decisions constrain subsequent formation. Per-instance ownership is a valid context; no global leader, term, log or fixed majority is assumed. One later Candidate may focus on only one core line. Keep necessary supporting behavior at its actual coordinate and explain cross_activity_effects rather than relabeling it.

Record applicability as applicable, externalized, not_applicable or unknown with actual sources and boundaries. Caller injection does not externalize an unread in-repository implementation. Preserve important unmapped Surfaces, including UNCLASSIFIED_PROTOCOL_RESPONSIBILITY. Reverse-check APIs, handlers, timers, storage, recovery, configuration and application boundaries as relevant, without claiming coverage from populated map entries.
