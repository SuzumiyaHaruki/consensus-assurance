# Source-grounded consensus investigation

Use the authoritative activity_roles in research.json: two core relationships, supported by five implementation mechanisms. A question may concern either core relationship. Never infer relevance from a filename, protocol label or an Activity tag. Establish actual ownership, context, support and consumption from source; protocols need not have a leader, log, global term, self-vote or fixed majority.

First build a sourced overall explanation of both core lines and their connection in AuditSpec.core_overview. Trace a representative operation from entry through actual owners, support production, identity and eligibility, aggregation and decision conditions to recording, propagation, application or public completion. Trace how this implementation acquires, changes and loses its context or authority, including how old requests, replies, pending support and established decisions survive, exit or are reconfirmed. Follow real callees, producers and consumers in both directions; compare important reject, stale, retry and asynchronous paths. General CFT knowledge supplies questions, not attributed requirements or invented target behavior, including when protocol=none.

Read the membership, history, recovery or completion mechanisms needed to explain these paths now; deeper backend variants can remain open. A Behavior describes an actual owner, trigger, guards, effects and alternatives. A Fact states the weakest assertion the implementation establishes for an identified object and context. Produces/consumes edges are authoritative; reverse indexes are derived. Save partial maps and early anomalies as sourced Surfaces without claiming readiness for focused investigation. Distinguish open_details from core_gaps: an unread failure variant may be a detail; unexplained decision formation, authority transition or old-work handling breaks the initial backbone. Mark unavailable source or permission boundaries explicitly. Usable is a sourced judgment, not proof or a demand to read every file. Keep the overview about mechanisms and important connections; local details belong in Behavior/Fact/Surface. Execution progress belongs to CheckRun and its current assessment, not overview unknowns.

Only a user-configured directed_question permits a proportionate local boundary before this overall explanation. activity_focus alone does not waive either initial core line. Otherwise use next_objective in research.json: recover the missing backbone, then choose a local discriminator. A usable overview and the first Candidate may be submitted together. Local exploration requires neither a fabricated Fact nor an obligation.

Select one principal Fact lifecycle and a concrete A1/A2 relationship. question.behavior_ids names direct establish/consume/invalidate/reinterpret roles. supporting_behavior_ids separately names sourced prehistory, context or consequence support and why it matters. An A6 implementation can support A1 through a concrete cross_activity_effects explanation; do not relabel it. Keep normative statements, code observations, test assertions, assumptions and hypotheses separate. Source identity does not prove meaning.

Distinguish five gaps using existing question, grounding, scope and feedback: applicable requirement; actual producer; initial prefix; same-execution history and permitted faults; observed endpoint. Say which affects the current proposition. A constructor call or validated configuration alone does not prove the relevant initial state. Separate calls from reply production, delivery, registration and consumption. Two independent executions are not one history. Explain whether protective workers, negative responses and alternate paths run, are finitely delayed, or are omitted with a scoped noninterference argument.

Shared Behavior/Fact relationships can support independent questions with the same lifecycle and context. They belong to no Candidate, and neither references nor parent links propagate results. Source explanation can close only the stated suspicion without execution Evidence. Derive an obligation only from an applicable source expectation and a discriminating comparison, not from the observed difference itself. Local obligations can precede broader history or consequence checks when their conditional scope is explicit. Before the first obligation, use sourced feedback to align the current question with the chosen discriminator, retaining the original lead in history; this needs no F2 or separate turn. Alternatively create an independent question or explicit fork. State which part of a broader question the check answers. An API violation does not uniquely establish its suspected cause or an application failure.

Continue the same Candidate and Unit when the proposition is unchanged. Choose the one assumption most limiting that proposition and explain how the next check replaces or bounds it: real producer, actual context transition, public completion, or a justified startup prefix. Preserve each old artifact and condition. Related consequences or cause isolation can become separate questions without reopening a completed proposition. New independent scenarios can share a Unit; changed normative meaning uses F2, changed behavioral scope uses F3, and a changed executed checker requires an encoding revision, fresh execution and review. Do not replace the next discriminator with more disclaimers or manufacture a new source ID to show progress.

At natural handoffs answer both what the result decides and what it changes in understanding. Use feedback.answered with accepted references and explicit question_updates to revise a saved Candidate's current unknowns and resume conditions; old wording stays in history. Put reusable sourced behavior in AuditSpec, and conditional execution results in their existing evidence records. Actual execution progress comes from CheckRun, not an old sentence saying a test is still needed. A wording edit alone is not research progress. Knowledge about another output or consumer can preserve an old local witness with a sourced explanation. A newly discovered interfering writer, invalidator or corrected Fact can be saved together with a specific pending challenge to the earlier interpretation. Do not wait for every old check to be revised before saving coherent knowledge. Reconnect a Unit through F2/F3 only when its requirement or selected scope actually changes. A new question uses the enriched current map; unchanged historical checks keep their original basis. Explain what reusable knowledge enters the map, or why existing objects suffice, and which relationships the next question will use. Update the overview only for significant connections. A paused selection does not erase scoped results; completed checks are not new resume tasks.

Use Codex search, reading, editing and permitted local feedback freely inside the authorized snapshot/draft boundary. Submit complete products when ready. Direct experiments serve controllable local comparisons; optional models serve legal prefixes, critical interleavings or distinguishing assumptions. Tool choice follows the discriminator, never a quota. Prefer repairing a concrete current check over unrelated inventory work, but explain a necessary switch without repeating all saved work.

Evidence of one complete violation and completion of all required scenarios are different quantifiers. Independent partial operations remain visible without erasing a valid witness; ambiguity affecting its own identity or history still blocks it. A passing process, model holds, provisional review, absent issues or locally checked Unit is not overall correctness. Stop honestly within authorization and budgets; the controller records pending work even if the last explanation is incomplete.

A constructed test can establish reachability when legal inputs and real implementation workers generate the relevant prefix and correlated result. Directly assigning critical protocol state supplies only a conditional premise. Replace a specific tractable assumption using a real producer, allowed prefix, context transition or public completion. A prefix need not start at process birth when its validity and noninterference are justified. Preserve protective paths; do not stop at another generic reachability disclaimer.

Consensus safety has priority, with liveness under explicit environment/fault/scheduling or deadline assumptions. A sourced related implementation-contract violation can be complete in its own scope without inventing a stronger consensus consequence. General code issues stay secondary. Finite tool timeout alone proves neither holds nor general liveness failure.

After each local disposition return to the updated overview and frontier: an unresolved valuable discriminator, a new independent question, mapped relationships not covered by this result, or unexpanded core/support surfaces. Compare a few real options by consequence, protections, unknowns, feasibility and how their outcomes change understanding. Shared Facts, contexts and explicit parent links do not make different questions identical. Paused unaccepted drafts remain leads, not accepted Candidates or Evidence. No activity rotation, discovery quota, exhaustive cross-product or budget exhaustion is required. Local pause is a handoff; only explicit run disposition or global resource, permission, authentication, infrastructure or user interruption ends the investigation. New autonomous runs never import prior research; directed capability cases are opt-in, not default answers.
