# File products for one native investigation

Read research.json for the current question, fixed artifacts, assessments, gaps and paths; state.json retains full history and source bindings. Write a complete submission.json using native-submission.schema.json. Product metadata schemas are in product-schemas.json. Source citations name authorized captured ranges. Rejected drafts and independent diagnostics are retained for whole-product repair.

- continue / pause / explained / obligation: select candidate_id or fork using parent_candidate_id, with a complete question. A fork explains holds/violated/incomplete effects on its parent. Pause supplies concrete resume_conditions. Explained states sourced protection and remaining scope, creating no Evidence. Obligation supplies one attributed claim and source bindings; construction may follow later.
- check / revise_check: select unit_id (its accepted Candidate is an alias) or create an obligation through candidate. Supply plan_path, harness_path and optional files mapping helper destinations to draft files. Harness source/files in metadata are empty; the controller captures executable bytes and selected adapter support. Never replace target code or dependency definitions. Revisions name previous_check_id; ordinary repairs preserve oracle, prerequisites and legality. Checker changes use encoding_revision and address an actual issue after fresh execution/review.
- research: supply a complete partial map_path, additive graph_path or scope_path. A map may accompany one graph/scope operation. semantic_revision supplies an attributed F2/F3 feedback_path for an existing unit_id and may carry a map. Graph additions cannot invent unowned executable Units.
- review: select artifact_id and inspect its fixed inputs, actual output and source dependencies. Supply whole-artifact checker_correspondence with concrete applicability/decomposition findings. no_issue_found has no counterevidence and is provisional. Resolve each old issue explicitly with its specific evidence; harness changes alone do not erase checker disputes.
- explore: submit a question, harness_path and optional files before or during candidate investigation. The clean-copy output guides construction but creates no property Evidence.
- model: optional; only when a verifier is configured. Read native-model-method.md. A model trajectory proposes an implementation history, never confirms it.
- stop: give scope, reason and rationale. Normal completion/no-actionable-direction needs source-owned ref_ids and bounded reasoning; focus no-actionable-direction also explains its frontier comparison. resource_limit, user_stop and tool_gap always stop without accepting attached semantic edits. Pending work and actual resources are controller facts, not a list to refill.

A formal question needs one principal fact_ids entry, lifecycle, direct behavior_ids, sourced A1/A2 relationship, contexts, event_paths, importance and trigger_rationale. Optional supporting_behavior_ids maps distinct Behavior IDs to their causal role. Partial maps are valid. audit_spec_version may be omitted for the current accepted basis. A map file's version is its accepted base (1 initially); the controller assigns the resulting version, including combined products. Never guess current+1 for a Candidate accompanying that map. The same base-version rule applies to questions in F2/F3 patches; the controller records resulting versions and normalizes only that metadata in declared changes.

map_changes attributes modified/deleted objects and added producers of current principal Facts by ID, impact (clarification/meaning/dependency), acquired source_ids and rationale. Explain whether new behavior affects this witness or only an independent consumer/consequence. Clarification cannot disguise changed identity/context or removal. Reconnect affected questions with reconnect_questions or the explicit Unit revision; unrelated enrichment and historical explained questions may retain their prior basis. A changed normative obligation needs F2; a changed dependency scope needs F3. Old evidence remains readable.

feedback can accompany any decision: accepted ref_ids, answered discriminator, remaining gap, understanding updated/unchanged/deferred, and rationale for the next discriminator/map disposition. Use it once to answer prior unknowns/counterevidence with sources, including through an accepted result's ownership. Do not repeat all historical feedback. A concrete switch rationale leaves controller-derived unfinished work visible. State actual initial prefix, fault control, same-history identities, independent result measurement and unobserved consequences in the existing scope/grounding/harness fields.
