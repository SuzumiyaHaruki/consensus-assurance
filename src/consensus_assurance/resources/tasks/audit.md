# File products for one audit investigation

Read research.json as this run's work index. A record locator names an existing JSON path, collection and exact match fields; paths are relative to the index directory unless absolute. Select matching records, then read field when present. Historical previews are navigation, not current pending work. Use artifact basis locators and graph_versions for old requirements, not the latest same-ID claim. Materials and execution IDs resolve through records in state.json. Full reviews, drafts and fixed inputs remain at their indexed paths.

Write a complete submission.json using submission.schema.json; product metadata schemas are in product-schemas.json. Source citations name authorized captured ranges. Follow next_objective; save core_overview formation/context/connection, source references, status and gaps under the analysis guide's initial-understanding rules. A partial map, feedback or exploration does not waive that boundary. A usable map and first Candidate may be submitted together.

When repairing a rejected product, set repair_of to its operation_id and submit the whole product. Diagnostics and archived drafts retain ownership; repeating identical errors may pause only that draft, not other questions sharing its Fact or context.

- continue / pause / explained / obligation: select candidate_id or fork using parent_candidate_id, with a complete current question. Sourced feedback may refine the discriminator before its first obligation; later requirement/scope changes use F2/F3. A fork explains holds/violated/incomplete effects on its parent. Pause supplies resume_conditions; explained cites the protective mechanism. Obligation supplies one attributed claim and source bindings. A complete check may be combined now, or constructed later.
- check / revise_check: select unit_id (or its Candidate alias), or create an obligation through candidate. Supply plan_path, harness_path and optional destination-to-draft files. Metadata source/files stay empty; the controller fixes executable bytes and adapter support. Never replace target code or dependencies. Revisions name previous_check_id. Ordinary repairs preserve requirement, oracle, identity and prerequisites. To replace driver legality, name repair_issue_ids and explain the actual changed inputs and sources in the new legality; reference every removed conflict's exact issue. This proposes an answer, not a resolution. Changed executed checker encoding uses encoding_revision.
- research: submit substantive feedback alone with acquired source or retained execution ref_ids, or a complete partial map_path, additive graph_path or scope_path. Feedback alone needs no Candidate or usable overview and creates no map version or Evidence. A map may accompany one graph/scope operation. semantic_revision supplies an attributed F2/F3 feedback_path for an existing unit_id and may carry a map. Graph additions cannot invent unowned executable Units.
- review: select artifact_id; omitted item target_id inherits it. Use review_contracts/review_questions: Direct Check requires checker_correspondence; other aspects are optional unless resolving an issue of that aspect. revision_needed names challenged_components. Resolve exact issue_ids using acquired Material source_ids, a concise answer and retained evidence_ids when relevant. For supplied conditions, use condition_dispositions with exact condition_id, sources and applicability; current_judgment remains unresolved. Unchanged sources and reasoning can be referenced, not recopied. The review guide defines semantic criteria. Candidate applicability review creates no execution Evidence.
- explore: submit a question, harness_path and optional files. Clean-copy output guides construction without property Evidence.
- model: optional when a verifier is configured; read model-method.md. A model trajectory proposes an implementation history, never confirms it.
- stop: give scope, reason and rationale. Candidate/family/focus stops are local handoffs; unfinished Units and disputes remain visible. Local pause supplies resume_conditions. Normal run/focus stops supply frontier_comparison entries with existing ref_ids, a concrete next_step, actionable (whether useful and feasible now), and rationale against current capacity and permissions. A run comparison must cover pending_work IDs, paused Candidate IDs, deferred/unclassified surface:<entry_point> IDs and an incomplete core_overview (target_profile if absent) unless user-directed; related references may share one explanation. No actionable step may coexist with a run stop, regardless of reason. Run resource_limit/tool_gap and every user_stop terminate without accepting attached semantic edits; they describe actual interruptions, not local evidence limits.

A formal question names one principal fact_ids entry, lifecycle, direct behavior_ids, sourced A1/A2 relationship, contexts, event_paths, importance and trigger_rationale. supporting_behavior_ids maps distinct Behavior IDs to their causal role. audit_spec_version may be omitted for the current basis. A map file's version is its accepted base (1 initially); the controller assigns resulting versions, including questions in combined products and F2/F3 patches. Do not guess current+1. Unchanged Candidates retain their historical basis.

The controller derives actual map differences and reverse indexes. map_changes explains modified/removed objects and new producers or consumers of an existing principal Fact, with impact (clarification/meaning/dependency), acquired source_ids and rationale. Use one preserves explanation for unchanged requirements, dependencies and observation scope, or challenges mapping saved Candidate IDs to specific disputed premises. A corrected principal Fact requires a challenge; clarification cannot disguise identity/context/edge changes or removal. Independent additions need no invented revision and may still challenge a prior interpretation.

Coherent knowledge and its issues are accepted together; unaffected checks retain their basis. reconnect_questions updates explicitly selected questions. ScopeUpdate/F3 expands dependencies under its existing write rules; changed normative or fault/configuration applicability uses F2. No-op maps create no version.

feedback records ref_ids, answered, remaining, optional understanding and next-discriminator rationale. question_updates maps Candidate IDs to semantic unknowns and resume_conditions; it cannot change requirements or erase counterevidence. CheckRun and assessments own current execution/review progress; remaining in historical handoffs is not a live task list.

Claim/Scope owns the requirement and applicability. Harness legality explains this execution's prefix, faults and treatment of protections; Monitor grounding explains event identity, prerequisites and the independent comparison. Cite claim_id/unit_id/binding_ids/source_ids with substantive local derivation and applicability instead of copying the Claim's full grounding. Never omit a new assumption or replace reasoning with "as above". Review addresses correspondence and new disputes; Feedback records only the research increment. claim.concern distinguishes consensus_safety, bounded_liveness and implementation_semantics, not confidence or severity.

Optional preflight: run validation.command followed by the draft-relative filename in an existing Codex tool call. It shares acceptance preparation, writes no accepted state and executes no target or model; formal submission rechecks fixed bytes and current state without a preflight ticket. capacity is the sole current budget snapshot. When time is short, submit the smallest complete sourced feedback before a larger map revision; a draft without a reliable receipt is not accepted.
