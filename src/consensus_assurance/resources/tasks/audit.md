# File products for one audit investigation

Read research.json for this run's question, fixed artifacts, assessments, gaps and paths; state.json retains only this run's history and source bindings. Write a complete submission.json using submission.schema.json. Product metadata schemas are in product-schemas.json. Source citations name authorized captured ranges. Rejected drafts and independent diagnostics are retained for whole-product repair.

Follow next_objective derived from the saved core_overview. Before default focused investigation, save formation, context and connection explanations with existing Behavior/Fact/source references, open_details, core_gaps, status and rationale inside the map. Incomplete maps remain useful; usable requires a sourced explanation of both lines without declared core breaks. Only the configured directed_question changes this initial boundary. Partial-map research and exploration remain available, and a usable map can accompany the first Candidate without an extra turn.

When repairing a rejected product, set repair_of to its operation_id. This preserves draft ownership before any Candidate is accepted. Independent diagnostics changing is construction progress; repeating the same diagnostics may pause only that draft. A different discriminator is not penalized for sharing a Fact, context or parent. Paused drafts remain in research.json and their complete archived files remain readable.

- continue / pause / explained / obligation: select candidate_id or fork using parent_candidate_id, with a complete current question. Before its first obligation, a sourced feedback.answered may explain a changed discriminator; prior questions stay in history, and a combined check can save map, question, obligation and files together. After an obligation, changed meaning or scope uses F2/F3. A fork explains holds/violated/incomplete effects on its parent. Pause supplies concrete resume_conditions. Explained states sourced protection and remaining scope, creating no Evidence. Obligation supplies one attributed claim and source bindings; construction may follow later.
- check / revise_check: select unit_id (its accepted Candidate is an alias) or create an obligation through candidate. Supply plan_path, harness_path and optional files mapping helper destinations to draft files. Harness source/files in metadata are empty; the controller captures executable bytes and selected adapter support. Never replace target code or dependency definitions. Revisions name previous_check_id; ordinary repairs preserve oracle, prerequisites and legality. Descriptive explanations may change with the repair; they cannot change its responsibility or fault assumptions. Every monitor names admission_alias from an declared harness prerequisite; list order never admits an operation. Checker changes use encoding_revision and address an actual issue after fresh execution/review.
- research: supply a complete partial map_path, additive graph_path or scope_path. A map may accompany one graph/scope operation. semantic_revision supplies an attributed F2/F3 feedback_path for an existing unit_id and may carry a map. Graph additions cannot invent unowned executable Units.
- review: select artifact_id and inspect its fixed inputs, actual output and source dependencies; a source-only Candidate review instead examines its saved question and specific knowledge challenge. Supply whole-artifact checker_correspondence explaining which current proposition and premises the actual observation answers, separating the original cause hypothesis and wider consequences. Include concrete applicability/decomposition findings. no_issue_found has no counterevidence and is provisional. revision_needed names challenged_components (configuration, initialization, driver, observation, oracle, expectation or scope), distinct from the review aspect. A configuration/input repair preserves the oracle; an oracle repair changes its encoding. Resolve an issue by issue_id, substantive rationale, acquired Material source_ids and optional evidence_ids for retained executions/artifacts/reviews. The controller reads the original version, question and source history; do not copy them into the resolution. A new artifact and matching execution must answer the actual challenged component, not an unrelated change.
- explore: submit a question, harness_path and optional files before or during candidate investigation. The clean-copy output guides construction but creates no property Evidence.
- model: optional; only when a verifier is configured. Read model-method.md. A model trajectory proposes an implementation history, never confirms it.
- stop: give scope, reason and rationale. Candidate/family stops release that local selection and continue the same investigation; unfinished Units and disputes stay visible. A local pause supplies concrete resume_conditions. Focus stops compare remaining authorized directions and return to selection. Normal run stops require frontier_comparison against known directions, permissions and remaining capacity; a checked Unit or one finding alone cannot justify exhaustion. Run resource_limit/tool_gap and every user_stop terminate without accepting attached semantic edits. Pending work and actual resources are controller facts, not a list to refill.

A formal question needs one principal fact_ids entry, lifecycle, direct behavior_ids, sourced A1/A2 relationship, contexts, event_paths, importance and trigger_rationale. Optional supporting_behavior_ids maps distinct Behavior IDs to their causal role. Partial maps are valid. audit_spec_version may be omitted for the current accepted basis. A map file's version is its accepted base (1 initially); the controller assigns the resulting version, including new Candidates in combined products. Existing unchanged Candidates retain their declared historical basis. Never guess current+1 for a Candidate accompanying that map. The same base-version rule applies to questions in F2/F3 patches; the controller records resulting versions and normalizes only that metadata in declared changes.

The controller derives actual before/after map edits, including core_overview; reverse indexes alone are mechanical. map_changes explains modified/removed objects and new producers or consumers of an existing principal Fact, using impact (clarification/meaning/dependency), acquired source_ids and rationale. On a shared object, give one preserves explanation for why the existing propositions, grounding, prehistory, identities, scope and observations still apply; do not repeat it for every neighboring Candidate. Alternatively, challenges maps saved Candidate IDs to specific challenged premises or interpretations. Independent additions need no invented old-object revision, but can explicitly challenge a sourced earlier interpretation. Different IDs or unchanged source code do not prove independence. A corrected principal Fact needs a concrete challenge; mere rewording can use clarification, which cannot disguise identity/context/edge changes or removal.

Knowledge growth is not a Unit scope revision. The controller accepts a coherent sourced map and records its specific challenges as pending applicability ReviewIssues in the same transaction, preserving fixed executions and historical evaluations. A current v3 map may coexist with a still-applicable v1 question, Unit and artifact; no blanket version bump, F3, reexecution or review call is required for an independent output. Historical IDs resolve in their original map. New questions use the current map. reconnect_questions explicitly reconnects selected questions; actual changes to an accepted requirement use F2 and elected dependency/scope expansion uses ScopeUpdate/F3. An interpretation correction is not automatically a normative change. No-op maps create no new version. Explain genuine effects even for checked, closed or explained Candidates; graph adjacency alone does not reopen them.

Keep core_overview as navigation within the same map: ordinary detail need not enter its references; significant protection/context connections should update representative references and explanation; an incorrect core explanation must update its gaps/status honestly. Review knowledge issues on the saved Candidate (artifact_id may name it, aspect applicability) or through its executed artifact. Resolve the exact issue with sourced reasoning; source-only review never creates execution evidence.

feedback can accompany any decision: accepted ref_ids, answered discriminator, remaining gap, optional understanding and rationale for the next discriminator/map disposition. question_updates maps explicit saved Candidate IDs to current unknowns and resume_conditions, supported by feedback's source ownership. It updates current understanding while retaining history; it cannot change the proposition, erase counterevidence or turn a conditional result into a code fact. Do not mechanically copy old unknowns into resume conditions. Candidate execution records are projected from actual checks. Claim.pending and grounding.unresolved retain proposal-time information; current execution, feedback and open issues determine present work. A concrete switch rationale leaves unfinished work visible. State actual initial prefix, fault control, same-history identities, independent result measurement and unobserved consequences in the existing scope/grounding/harness fields.

Use claim.concern to distinguish consensus_safety, bounded_liveness and implementation_semantics. This identifies the proposition, not its evidence strength or severity. A timeout without a sourced deadline/fairness contract is incomplete observation, not general liveness failure. Existing scope and grounding state the contract and excluded consequences.

After a scoped result, explanation, bounded negative check or concrete pause, update this run's understanding and compare its frontier for another sourced discriminator. Mapped does not mean all relationships were checked. Compare protections, what the next result would decide, and needed capability. Yield repeatedly uninformative local construction with its exact diagnostics; it does not terminate other research. Candidate/family stops affect only the explicitly named Candidates, not inferred relatives. Remaining counts are in capacity; do not create obligations that cannot be checked with authorized resources.
