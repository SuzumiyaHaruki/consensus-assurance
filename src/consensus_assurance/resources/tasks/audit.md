# One file-backed update

Use research.json as current navigation for source/draft paths, questions, results, necessary gaps, changed knowledge, build inputs and allocation. Explicitly abbreviated previews are not complete records; state.json and referenced artifacts retain the full records and history. Start with the small update example; consult only needed $defs in submission.schema.json, not the whole schema.

Write the update as JSON in draft. The final response is a separate JSON object: {"submission":"update.json","summary":"Short summary"}, using the draft-relative path, with no Markdown or trailing prose. Summary briefly states this turn's actual change, action and incomplete work; the current account remains in Interpretation. Optional validation.command reports validity and, for valid updates, no_change, execution_requested and derived effects against saved state: record creation, update, interpretation append or unchanged. It does not accept, execute or reserve capacity; effects describe record changes, not semantic correctness or research progress. Acceptance reads retained bytes. Rejected whole drafts and diagnostics return for ordinary repair in this session; editable drafts never override receipts.

The update file requires rationale explaining what the action aims to clarify, test or correct and what changed; Interpretation.rationale holds the current question account, not a prefixed revision log. Sources, investigations, knowledge, gaps, interpretations, experiment, repeat_experiment_id and stop are optional. Existing records use explicit IDs. Unique @names may refer to new questions/knowledge within a batch. The controller assigns IDs, revisions and comparison indices. Source IDs identify acquired file/ranges; do not create aliases merely to count handoffs. For local corrections, read the full current record, copy its fields accepted by the relevant submission schema into draft, and edit with native tools or a short script. Exclude controller metadata absent from that schema. Knowledge and Interpretation updates remain complete current accounts, not partial patches; keep intended references and conditions. Optional preflight effects help inspect the actual changes.

- investigations: create a sourced question or update specified fields of id. Hypothesis/discriminator may be provisional; update the same id as evidence changes them. For continued inquiry, discriminator states information that could change the judgment; completed comparisons belong in Interpretation. parent_id links a child without closing its parent. paused needs resume_conditions. Current counterevidence and limitations belong only to Interpretation, including source-only accounts.
- knowledge: behavior/fact statement, conditions and sources, optionally execution indices and direct knowledge uses. References specify exact entry_id/revision and optionally the assertion used. Correct an existing id using changed_premise; affected_uses identifies affected terminal investigations/experiments/interpretations through recorded direct or derived uses, including older revisions, not every reachable use automatically. Supplement a correction's affected uses without gratuitous body changes. Revise derived knowledge under its own id where needed. Old bases remain available. Failed-receipt knowledge citations require an applicable Interpretation.failure_attribution covering the cited witness or its correlated prerequisites; the interpretation may be in this update.
- gaps: necessary question under investigation_id; optional experiment_id limits it to that experiment and successors. Put broader directions in discriminator or Interpretation.limitations. Interpretation.answers maps exact gap IDs to {"explanation":"Specific sourced/observed basis", "resolved":false}. Set resolved=true only when that basis resolves the gap; false records partial progress or reopens it. Omitted IDs retain earlier answers. Identical updates do not duplicate gaps.
- interpretations: investigation_id, optional experiment_id, source_ids, rationale and conclusion (explained, conditional, violated, holds, unresolved) describes the comparison/evidence interpretation, not a defect verdict. Required defect_claim is asserted (a sourced defect under stated valid conditions), refuted (the suspicion is defeated), unresolved (a necessary uncertainty remains), or null (no current defect judgment). There is no inheritance. Follow evidence-review for the current account, counterevidence and limitations. executions maps receipt IDs to decisive parsed indices. Setting experiment_id requires that experiment's receipt; a question needs no dedicated execution. Question-level explained/conditional/unresolved accounts omit experiment_id and can reuse applicable receipts across questions. Explained/conditional/unresolved accounts may cite failed receipts without claiming a completed comparison. Separate producer receipts need joint_history. Preserve explicit knowledge uses.
- experiment: one invocation with investigation_id, harness_path, optional files (workspace destination → draft path), source_ids, scope and prefix, including supplied assumptions. requirement/responsibility and comparisons are optional; requirements need verified anchors, which do not prove source meaning. A comparison owns event, identity_fields, admission_alias, assertion and optional antecedent/applicability_conditions. Only its admission and referenced aliases plus their transitive dependencies are required; link necessary history explicitly, not by array order. For alternative setup events mode=A/B, use separate admissions with mode conditions and independent result applicability; never filter on the measured result. Cases/controls can share execution. Keep reusable helpers; when accumulated scenarios obstruct the current question, make its case and necessary controls independently selectable through test_names where supported. Omitted/null selects all generated tests; a nonempty list selects exact Go TestAssurance top-level names (including their subtests) full Rust test names, or Java method names within the generated class. Python has no case selector. Selection controls execution, not compilation, initialization or shared state. Fixed artifacts retain earlier scenarios, and explicit repeat retains its saved selection. Changed basis uses previous_id/revision_reason and fresh execution.
- repeat_experiment_id: execute the selected fixed experiment's saved inputs in a clean copy, not current drafts or another version. Explain its research purpose in rationale following consensus-analysis. Mutually exclusive with experiment and stop; consumes one execution and the existing time budget. The new receipt belongs to that fixed experiment; cite its exact CheckRun ID. Ordinary unchanged submissions remain deduplicated.
- stop: bounded_completed only for a preconfigured finite directed task with no necessary unfinished work. Cancellation, service refusal, permission loss and exhausted resources are controller boundaries, not model declarations.

Go execution_package selects one captured local package; Rust selects a crate and tests/<basename>.rs; Python has no package override. Rust experiments may select features (Cargo feature names), default_features (default true), and all_features (default false) without editing manifests or locks. These options select the tested build variant; explain its applicability in scope and use a successor when changing an existing experiment's variant. Omission preserves the crate's default selection. Follow backend instructions for protected source, dependencies, locks, support and caches. Exploration and specified checks use identical fixed-input isolation. Agent shell networking is disabled; executor communication is confined to its private namespace.

Exact unchanged updates receive no_change without duplicate revisions or automatic stopping; source reading and draft construction may continue. Current navigation provides bounded outcomes, corrections and full-record locators for choosing and undertaking further inquiry. Turn allocation and CheckRun establish timing; sampled allocation and preflight elapsed time are checkpoints, not live timers. Expiry needs no closing submission.
