# File products for one audit investigation

Read research.json for selected work and shared relationship navigation; comparison_refs is only the minimum normal-stop accounting. A record locator names an existing JSON path, collection and exact match fields; paths are relative to the index directory unless absolute. Select matching records, then read field when present. Historical previews are navigation, not current pending work. Use artifact basis locators and graph_versions for old requirements, not the latest same-ID claim. Materials and execution IDs resolve through records in state.json. Full reviews, drafts and fixed inputs remain at their indexed paths.

Existing review items may carry optional short Chinese report_title/report_answer for their target. This presentation-only exception does not replace English rationale, conditions, measured fields or the controller verdict. Omission never blocks work; do not add a translation or closing turn.

Write a complete submission.json using submission.schema.json and product-schemas.json. Cite authorized captured ranges. Follow next_objective and the analysis guide for core_overview readiness; a usable map and first Candidate may share a submission.

When repairing a rejected product, set repair_of to its operation_id and submit the whole product. Diagnostics retain ownership: reconsider=submission calls for product repair; reconsider=research_decision supplies contradictory facts, references and capacity for a new research decision. Editing a reason or boolean is not new basis. Repeated errors may pause only the draft, never unrelated questions.

- continue / pause / explained / obligation: select candidate_id or fork using parent_candidate_id, with a complete current question. Sourced feedback may refine the discriminator before its first obligation; later requirement/scope changes use F2/F3. A fork explains holds/violated/incomplete effects on its parent. Pause supplies resume_conditions; explained cites the protective mechanism. Obligation supplies one attributed claim and source bindings. A complete check may be combined now, or constructed later.
- check / revise_check: select unit_id (or its Candidate alias), or create an obligation through candidate. Supply plan_path, harness_path and optional destination-to-draft files. Metadata source/files stay empty; the controller fixes executable bytes and adapter support. Never replace target code or dependencies. Revisions name previous_check_id. Driver legality repairs name repair_issue_ids and explain changed inputs and sources; reference every removed conflict's exact issue. Changed executed checker encoding uses encoding_revision.
- research: submit substantive feedback alone with acquired source or retained execution ref_ids, or a complete partial map_path, additive graph_path or scope_path. Feedback alone needs no Candidate or usable overview and creates no map version or Evidence. A map may accompany one graph/scope operation. semantic_revision supplies an attributed F2/F3 feedback_path for an existing unit_id and may carry a map. Graph additions cannot invent unowned executable Units.
- review: select artifact_id; omitted item target_id inherits it. Use review_contracts/review_questions: Direct Check requires checker_correspondence; other aspects are optional unless resolving an issue of that aspect. revision_needed names challenged_components. Resolve exact issue_ids using acquired Material source_ids, a concise answer and retained evidence_ids when relevant. For supplied conditions, use condition_dispositions with exact condition_id, sources and applicability; current_judgment remains unresolved. Unchanged sources and reasoning can be referenced, not recopied. The review guide defines semantic criteria. Candidate applicability review creates no execution Evidence.
- explore: submit a question, harness_path and optional files. Clean-copy output guides construction without property Evidence.
- model: optional when a verifier is configured; read model-method.md. A model trajectory proposes an implementation history, never confirms it.
- stop: local scopes release named work; unfinished Units and disputes remain. For run/focus, frontier_comparison gives ref_ids, the smallest useful next_step, actionable and rationale; run comparisons cover frontier.comparison_refs and cannot declare an actionable option. Group shared obstacles, cite existing results instead of resummarizing them. user_stop and run resource_limit/tool_gap are controller events, never submission authority; a local tool/resource gap can use a local stop with resume_conditions. Normal run reasons are bounded_completed, insufficient_basis or no_actionable_direction.

A formal question names one principal fact_ids entry, lifecycle, direct behavior_ids, sourced A1/A2 relationship, contexts, event_paths, importance and trigger_rationale. supporting_behavior_ids maps distinct Behavior IDs to their causal role. audit_spec_version may be omitted for the current basis. A map file's version is its accepted base (1 initially); the controller assigns resulting versions, including questions in combined products and F2/F3 patches. Do not guess current+1. Unchanged Candidates retain their historical basis.

The controller derives actual map differences and reverse indexes. map_changes explains modified/removed objects and new producers or consumers of an existing principal Fact, with impact (clarification/meaning/dependency), acquired source_ids and rationale. Use one preserves explanation for unchanged requirements, dependencies and observation scope, or challenges mapping saved Candidate IDs to specific disputed premises. A corrected principal Fact requires a challenge; clarification cannot disguise identity/context/edge changes or removal. Independent additions need no invented revision and may still challenge a prior interpretation.

Coherent knowledge and its issues are accepted together; unaffected checks retain their basis. reconnect_questions updates explicitly selected questions. ScopeUpdate/F3 expands dependencies under its existing write rules; changed normative or fault/configuration applicability uses F2. No-op maps create no version.

feedback records ref_ids, answered, remaining, optional understanding and next-discriminator rationale. question_updates maps Candidate IDs to semantic unknowns and resume_conditions; it cannot change requirements or erase counterevidence. CheckRun and assessments own current execution/review progress; remaining in historical handoffs is not a live task list.

Claim/Scope owns requirement and applicability; Harness legality owns this history and caller duties. A formal Monitor answers an independent implementation responsibility. Initialization, observation validity and driver compliance usually belong in prerequisites, controls or diagnostic events, not duplicate properties. Never filter observations using the expected property outcome; continue the declared legal schedule and retain potential violations even when a control fails. Ground monitors through actual identity, prerequisites and independent comparison. Cite accepted grounding, explain new assumptions and review only the required correspondence or dispute. claim.concern classifies responsibility, not confidence.

Optional preflight: run validation.command followed by the draft-relative filename in an existing Codex tool call. It shares acceptance preparation, writes no accepted state and executes no target or model; formal submission rechecks fixed bytes and current state without a preflight ticket. capacity is the current budget snapshot: new_obligation is an entry capability, not a complete check/review budget; remaining.agent_calls counts future turns, not local work in this running turn. A reliable receipt fixes only declared product files before deadline handling; saved bytes are not acceptance or Evidence. Without a reliable receipt, draft files remain unsubmitted. Natural expiry needs no closing submission; small feedback is useful only for new knowledge.
