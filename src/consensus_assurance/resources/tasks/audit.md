# File submissions

Read research.json for source/draft locations, current work, actual resource capacity and retained record locators. A locator gives a JSON path, collection and match fields. Materials and CheckRun IDs resolve in state.json; old artifacts use their recorded graph_versions and basis locators, not the latest same-ID claim. The continuation message directly includes the last operation's state, result paths and known gaps; consult raw records when needed.

Write a complete submission file matching submission.schema.json and return its draft-relative path and summary. Declare source ranges using authorized captured files. All actions may carry feedback, map_path/map_changes and one review alongside their main action. At most one target execution is requested per submission. Optional preflight uses validation.command plus the draft-relative filename; it shares read-only preparation, reserves no budget and supplies no acceptance ticket. Formal acceptance rereads retained bytes against current state.

- continue / pause / explained / obligation: a new question needs question text and source_ids; other AuditQuestion fields add useful context. With candidate_id, question may contain only changed fields or be omitted. parent_candidate_id creates a related child without changing the parent. Pause names concrete resume_conditions; explained retains sourced counterevidence and explained_by_existing_mechanism. An obligation adds one sourced claim and physical bindings; omitted binding associations are derived from that claim, without inferring source semantics.
- check / revise_check: select an existing unit_id or its Candidate alias, or supply candidate with action=obligation to create and check together. Supply plan_path, harness_path and optional files mapping workspace destinations to draft files. Leave plan.harness.source/files empty; the controller fixes their bytes. Omitted plan.claim_id/binding_ids select the Unit's accepted responsibility and bindings. Revisions name previous_check_id and rationale. Optional revision is a GraphPatch changing that check's accepted claim/bindings/Unit under expected_versions; actual diffs are recorded. Use one revision path for setup, history, predicate, observation or requirement corrections. A changed claim gets new execution, not old confirmation.
- explore: question, harness_path, optional files and execution_package run through the same clean-copy execution boundary without a formal property verdict. Retain actual incomplete outputs and the supplied-state/history gap.
- research: sourced feedback, a partial map and/or a result review, with no preliminary Candidate. Feedback uses ref_ids, answered, remaining and rationale. Explicitly include each CheckRun being explained; shared sources or harness names do not associate executions. Optional question_updates changes current unknowns/resume_conditions while retaining earlier questions. Identical adjacent unchanged handoffs may receive informational duplicate_of; there is no repetition penalty or forced execution.
- stop: explicit candidate/family/focus disposition retains unresolved work and conditions. Only a preconfigured directed_question may end with run/bounded_completed after its finite task is disposed. Open investigations continue useful work within resource limits; actual cancellation, service refusal, lost permissions and exhausted budgets belong to the controller.

review contains artifact_id, review_items and optional resolutions; omitted item target_id inherits artifact_id. Direct checks require checker_correspondence; applicability/decomposition are optional unless answering a specific issue. Candidate applicability reviews require no execution. A review can accompany research, a corrected map or the next check/exploration. revision_needed names challenged_components; resolutions identify exact issue_id, acquired source_ids and retained evidence_ids. Supplied condition IDs require sourced dispositions; current_judgment stays unresolved. Keep independent boundaries and contrary evidence. Consult evidence-review for the substantive criteria, not a self-certification flag.

Maps are optional. Behavior/Fact/Activity references, when supplied, must exist in the recorded map version. Map version is its accepted base (1 initially); the controller assigns the result. map_changes supplies source_ids and rationale for changed premises actually referenced by saved questions, with preserves explaining unaffected interpretations or challenges identifying specific Candidate IDs. Independent additions need no declarations; no-op maps create no version. Reverse indexes are derived. Do not fabricate one principal Fact or core Activity tags to start local work.

For Go, optional execution_package selects one captured local package and the configured main-file basename; helpers stay workspace-relative. For Rust it selects a captured crate and tests/<configured basename>.rs. Consult research.build_inputs and backend instructions for fixed lock, effective features, tools and cache policy; source declarations alone do not establish active cfg. Python has no package override. Never replace target code, dependencies, manifests, locks, build scripts or tool configuration. Compilation/setup errors use the same successor path. Formal process outcome, matched observations and semantic interpretation remain distinct.

For rejected products, retain diagnostics and set repair_of to that operation ID when submitting a corrected complete draft. Rejection does not silently pause other questions. Deliver independently useful source answers or execution feedback when ready; do not wait for an entire map, obligation or all trials. Map and review changes can travel with the next useful action. The current turn's allocation and CheckRun establish timing; research/preflight elapsed_seconds is only the last saved checkpoint. A reliable completion receipt fixes declared files; unfinished drafts are not accepted evidence. Expiry requires no extra wrap-up.
