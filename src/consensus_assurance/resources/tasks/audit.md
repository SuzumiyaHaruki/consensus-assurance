# File products for one audit investigation

Read research.json for selected work and shared relationship navigation. A record locator names an existing JSON path, collection and exact match fields; paths are relative to the index directory unless absolute. Select matching records, then read field when present. Historical previews are navigation, not current pending work. Use artifact basis locators and graph_versions for old requirements, not the latest same-ID claim. Materials and execution IDs resolve through records in state.json. Full reviews, drafts and fixed inputs remain at their indexed paths.

When capacity permits, supply an optional short Chinese report_title and one to three report_answer sentences with decisive conditions in review items. Keep English semantic reasoning; actual verdicts and measurements prevail. Omission never blocks work or warrants a translation turn.

Write a complete submission.json using submission.schema.json and product-schemas.json. Cite authorized captured ranges. Follow next_objective and the analysis guide for core_overview readiness; a usable map and first Candidate may share a submission.

When repairing a rejected product, set repair_of to its operation_id and submit the whole product. Diagnostics retain ownership: reconsider=submission calls for product repair; reconsider=research_decision requires a different research action, not field repair of an unauthorized stop. Repeated errors may pause only the draft, never unrelated questions.

- continue / pause / explained / obligation: select candidate_id or fork using parent_candidate_id, with a complete current question. Sourced feedback may refine the discriminator before its first obligation; later requirement/scope changes use F2/F3. A fork explains holds/violated/incomplete effects on its parent. Pause supplies resume_conditions; explained cites the protective mechanism. Obligation supplies one attributed claim and source bindings. A complete check may be combined now, or constructed later.
- check / revise_check: select unit_id (or its Candidate alias), or create an obligation through candidate. Supply plan_path, harness_path and optional destination-to-draft files. Metadata source/files stay empty; the controller fixes executable bytes and adapter support. Never replace target code or dependencies. Revisions name previous_check_id. Driver legality repairs name repair_issue_ids and explain changed inputs and sources; reference every removed conflict's exact issue. Changed executed checker encoding uses encoding_revision.
- research: submit substantive feedback alone with acquired source or retained execution ref_ids, or a complete partial map_path, additive graph_path or scope_path. Feedback alone needs no Candidate or usable overview and creates no map version or Evidence. A map may accompany one graph/scope operation. semantic_revision supplies an attributed F2/F3 feedback_path for an existing unit_id and may carry a map. Graph additions cannot invent unowned executable Units.
- review: select artifact_id; omitted item target_id inherits it. Carries feedback, not a map. Use review_contracts/review_questions: Direct Check requires checker_correspondence; other aspects are optional unless resolving an issue of that aspect. revision_needed names challenged_components. Resolve exact issue_ids using acquired Material source_ids, a concise answer and retained evidence_ids when relevant. For supplied conditions, use condition_dispositions with exact condition_id, sources and applicability; current_judgment remains unresolved. Unchanged sources and reasoning can be referenced, not recopied. The review guide defines semantic criteria. Candidate applicability review creates no execution Evidence.
- explore: submit a question, harness_path and optional files. Clean-copy output guides construction without property Evidence.
- stop: candidate/family/focus release local work; unfinished Units and disputes remain. A local tool/resource gap supplies resume_conditions. Open runs reject scope=run: continue with research, exploration or another Candidate within remaining authorization. Only a preconfigured finite directed_question may end with run/bounded_completed after its task is disposed; cite the explained, closed or checked Candidate. Cancellation, permission/service failure and exhausted time/calls are controller events, never submission authority.

A formal question names one principal fact_ids entry, lifecycle, direct behavior_ids, sourced A1/A2 relationship, contexts, event_paths, importance and trigger_rationale. supporting_behavior_ids maps distinct Behavior IDs to their causal role. audit_spec_version may be omitted for the current basis. A map file's version is its accepted base (1 initially); the controller assigns resulting versions, including questions in combined products and F2/F3 patches. Do not guess current+1. Unchanged Candidates retain their historical basis.

The controller derives actual map differences and reverse indexes. map_changes explains modified/removed objects and new producers or consumers of an existing principal Fact, with impact (clarification/meaning/dependency), acquired source_ids and rationale. Use one preserves explanation for unchanged requirements, dependencies and observation scope, or challenges mapping saved Candidate IDs to specific disputed premises. A corrected principal Fact requires a challenge; clarification cannot disguise identity/context/edge changes or removal. Independent additions need no invented revision and may still challenge a prior interpretation.

Coherent knowledge and its issues are accepted together; unaffected checks retain their basis. reconnect_questions updates explicitly selected questions. ScopeUpdate/F3 expands dependencies under its existing write rules; changed normative or fault/configuration applicability uses F2. No-op maps create no version.

feedback.ref_ids identifies the answered Candidate, Behavior, Fact or surface:<entry_point> and supporting sources/executions. understanding records learning, not a map change. Apply the guide's related-map handoff in the next eligible product. question_updates revises Candidate unknowns/resume_conditions with sources, preserving requirements and counterevidence. Historical remaining is then-remaining; current execution/review records remain authoritative.

Claim/Scope owns requirement and applicability; Harness legality records this history and caller duties. Use the evidence-review guide and experiments reference for independent monitoring, identity, prerequisites, completion and attribution. claim.concern classifies responsibility, not confidence.

Optional preflight: run validation.command followed by the draft-relative filename in an existing Codex tool call. It shares acceptance preparation, writes no accepted state and executes no target; formal submission rechecks fixed bytes and current state without a preflight ticket. capacity is the current budget snapshot: new_obligation is an entry capability, not a complete check/review budget; remaining.agent_calls counts future turns, not local work in this running turn. A reliable receipt fixes only declared product files before deadline handling; saved bytes are not acceptance or Evidence. Without a reliable receipt, draft files remain unsubmitted. Natural expiry needs no closing submission.
