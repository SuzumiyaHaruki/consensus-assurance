## 实际观察与可解释机制

选题从“高任期负面心跳回复是否应刷新联系时间”收敛到更明确的区别：**根本没有远端处理或回复时，失败的流水线 future 是否仍被当成新的联系证据**。前一问题的反证被保留：租约关注连通性，收到负面回复未必不算联系，不能把它与无回复超时混为一谈。

正式场景使用两个 Voter，手工设置本地 Leader、已过期 4 秒的联系标记、2 秒租约；实际内存 transport 的超时为 40 毫秒。接收端只有 transport，没有 Raft worker，排队请求不被处理和回复。分别完成流水线／普通复制，再手工调用实际 `checkLeaderLease`。

| 实际路径 | 完成后的联系标记 | 手工租约检查结果 |
| --- | --- | --- |
| 流水线请求超时 → `pipelineDecode` | 刷新到当前时间 | Leader |
| 普通请求超时 → `replicateTo` | 保留过期标记 | Follower |

修复版 [原始输出](../runs/2026-09-27_13-22-02-hashicorp_raft-real-run/logs/55c79fd4cf55497a81166bce840a1c45/stdout.log) 中，8 个事件完整关联；有效违反见证为索引 3，对照结果为索引 7，无缺失、歧义或解析错误。两版 assessment 都记录 `comparison_complete=true`，当前归因为 `confirmed=false`。

源码能够解释这个局部差异：

1. [inmem_transport.go](../runs/2026-09-27_13-22-02-hashicorp_raft-real-run/native-source/inmem_transport.go) 的超时分支把 error 写入 future 后仍送入完成通道。
2. [replication.go](../runs/2026-09-27_13-22-02-hashicorp_raft-real-run/native-source/replication.go) 的 `pipelineDecode` 读取 Request／Response，没有先检查 `Error()`；检查更高任期后刷新联系时间，随后才根据 `Success=false` 退出。
3. [raft.go](../runs/2026-09-27_13-22-02-hashicorp_raft-real-run/native-source/raft.go) 的 `checkLeaderLease` 根据 Voter 的联系时间判断是否达到多数；被刷新的标记因此影响此次本地决策。

这支持“实际内存传输路径下的条件式局部责任违反候选”，尚不支持完整系统故障。Leader 初始状态和过期标记不是一次合法选举历史的观测结果；自动租约调度、pipeline 退出后的普通复制、心跳、来包和 VerifyLeader 并发保护均未运行。没有客户端成功、陈旧应用读取、错误提交或持续保留角色时长的证据，也不能外推到生产网络 transport。

辅助层文件确实随三次执行固定输入并编译，但三份 harness 均没有调用 `NewAssuranceCluster`；它们仍直接构造 `Raft`。因此本次没有验证新增辅助层能否帮助原生调查建立完整启动和选举前史。

## 配置已修复，为什么结果仍未确认

第一次复核正确发现：harness 使用 `DefaultConfig` 的 1 秒 Heartbeat／ElectionTimeout，却把 LeaderLeaseTimeout 改为 2 秒，并直接存入配置。该组合不满足 `ValidateConfig`，所以原局部观察不能归因于受支持配置。

后来受理的 [v2 harness](../runs/2026-09-27_13-22-02-hashicorp_raft-real-run/direct-checks/963f63f44ea14e70b8b33b55f11f1062/assurance_generated_test.go) 已把 HeartbeatTimeout、ElectionTimeout 都设为 2 秒，并在输出前调用 `ValidateConfig`；第二次正式执行成功，仍重现同一差异。比较两个受理的 plan，变化只有 `harness.source`，义务、oracle、前提及其他计划字段完全相同。

但关闭旧问题的三个提交依次被拒：

| 提交 | 具体原因 |
| --- | --- |
| `0e540fe4` | `target_version` 填修复制品版本 2，控制器要求原问题版本 1 |
| `ad9bee01` | 改回版本 1，但把制品 ID、执行 ID 写入只接受 Material ID 的 `source_ids` |
| `fc7bba68` | 移除非 Material ID 后，遗漏原问题的 `src-replication-progress`、`src-verify` 来源范围 |

前两次得到同一句泛化错误，无法直接看出分别是版本错误和引用类型错误。第三次诊断也没有指出缺失来源的具体 ID。原问题包含配置缺陷、已有保护和前史边界的大段综合说明，使局部关闭问题需要重复搬运大量无变化内容。

更深的规则冲突在 [reviews.py](../src/consensus_assurance/workflow/reviews.py)：任何 `checker_correspondence + revision_needed` 都设置 `needs_recheck=true`，关闭时又要求 `observable_properties` 或 `monitors` 有变化。这把“需要新执行”硬编码成了“需要改变 oracle”。本次修正的是配置，正确修复恰好应保留 oracle；而 `validate_check_revision` 也要求普通修复保留 oracle。

为确认不是推测，对最终退稿和 Analysis 的内存副本，仅补回上述两个原始来源到 resolution 与对应 review item，再调用现有 `accept_review`。实际下一条拒绝为：

```text
ValueError: Checker issue requires a changed oracle and actual matching reexecution
```

这个条件没有在真实运行中被走到，因为更早的引用检查先失败；它是本次只读分析发现并在内存副本上复现的后续阻塞。没有改原状态，也没有替 Agent 自动批准复核。即使只延长预算，合法的配置修复仍会遇到这一规则冲突。
