# 运行工作流

`audit-products-v60` 使用一条调查和执行路径。Codex 在授权源码快照中阅读、搜索，在草稿目录编辑；控制器保存材料、按操作身份提交产品，从干净副本运行实际实现并留存原始输出。

## 提交与继续

- `continue / pause / explained / obligation` 保存有来源的问题及处置。已有问题用 ID 和变化字段更新；没有地图、完整义务或判据也可以继续调查。只有明确暂停才改变该问题的处置。
- `check` 选择已保存义务，或者同时携带一个新问题、义务及完整检查。绑定关联和 plan 中省略的义务／绑定 ID 可由选定 Unit 推导，源码含义不自动推导。
- `explore` 使用同一执行后端和隔离路径，不形成正式性质判定；失败、部分输出及条件状态均保留。
- `revise_check` 指定前驱和原因，提交新制品；必要时通过带 `expected_versions` 的 `revision` 修改该检查的义务／绑定／Unit。控制器保存实际差异，重新执行。已被替代的制品仍可查阅，不能复用其观测为新确认。
- 所有提交都可带 `review`、反馈和可选地图更新；`research` 用于只有这些内容的交接。结果复核、学习和下一检查不必分成三轮。

每个操作最多请求一次目标执行。完整文件先在副本上预检，预检不计预算、不产生受理凭证；正式受理仍读取实际提交文件。诊断与完整拒绝稿交回同一会话修订，使用 `repair_of` 关联，重复错误不自动暂停其他问题。正式提交按操作身份恢复，不能重复执行或重复提交知识版本。

## 状态和证据

`research.json` 是当前视图和记录索引，包含问题、实际剩余能力、未决前提、制品和执行位置。后续消息直接提供上一操作摘要；具体 CheckRun、原始输出及必要缺口需要读其定位记录。反馈明确引用所解释的执行，不能按相同源码或驱动名称归属。

可选地图按变化保存版本；已引用的前提变化需要来源和受影响解释，独立新增无需声明。问题历史、义务版本、图提交和旧制品保留旧依据。当前焦点仅为导航；子问题用显式父 ID 关联，不自动消解父命题。

复核区分适用性、义务分解和检查对应性，但无需分阶段提交。当前结论必要的未决条件、相反观测和既有争议保持开放；无问题意见不能自动覆盖它们。结果展示区分进程状态、测量及语义结论，局部结果不升级为整体正确性判断。

## 实际资源与恢复

只保留模型调用数、目标执行数、总时间、单回合及单动作时限。探索和失败执行也消耗真实执行次数；没有 Unit、修订、复核或图对象配额。开放调查继续有用工作到资源边界，局部暂停后可重新选题。真实取消、拒绝和权限失败由控制器终止，不靠模型宣称。

使用原生同一会话续接；每个新 run 独立。源码与可信指令只读、草稿可写、凭据隔离、目标执行隔离和子进程清理保持原边界。Go 包、Rust crate／feature 和构建缓存继续由已有后端处理。

旧方法不能在当前代码下静默恢复。恢复前先检查方法版本，旧归档在原 Git 版本下读取／执行。新本地配置需从当前未授权模板生成；退役配额字段会给出不兼容诊断。历史报告不按新方法重写。

主要代码入口：`workflow/audit.py` 统一准备、受理和执行，`audit_spec.py` 可选地图及版本关联，`direct_checks.py` 固定检查和观测，`reviews.py` 争议与证据解决，`research.py` 当前视图及短摘要。机械文件合同和实际加载路径由 `resources/task-skills.json` 指定。
