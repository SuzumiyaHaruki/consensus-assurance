# 运行工作流

本项目使用 Codex 完成共识实现审计。搜索、阅读、编辑、工具反馈和调查续写交给 Codex 会话；本项目提供领域方法、研究产物校验、隔离的正式执行以及有来源和边界的证据记录。生产树只有这一条调查主线，离线回复替身也经过同一个提交入口。

## 调查与产物

每次 `run` 使用新目录、空研究状态和新 Codex 会话，显式关闭跨会话记忆读取和生成；其他运行的报告、草稿和结论不作为输入。`resume --run` 只延续明确指定的同一次运行。新开始拒绝使用非空实验目录。选题和检查依照 Activity → Behavior → Fact → Candidate → Obligation → Evidence 的依赖关系从当前源码推进，不预设某个历史场景。

`agent-source` 只公开获准的目标快照文件，`draft` 可写。目标 AGENTS.md、SKILL.md、凭据和范围外文件被排除；本次运行的源码和保留证据只读，其他运行目录不可读。可信方法由 `resources/task-skills.json` 加载并记录路径、版本，保存为 `audit-method.md`。Codex 先读本次精简 `research.json`，按 `record` 的文件、集合和精确匹配条件展开所需对象；相对路径以索引所在目录为基准。`state.json` 保存原文和完整历史，不要求每轮通读。引用仍校验路径、行范围和快照版本，定位有效不意味着语义判断成立。

默认先在 AuditSpec.core_overview 解释共识形成与推进、上下文／权威转换及二者连接。部分地图仍可受理；概览有核心断点时，`research.json.next_objective` 指向补齐主干；概览可用后指向集中调查与回流。仅用户配置的定向问题可采用局部边界。保存概览和首个问题可以合并为一次提交，控制器不另设调查阶段或阅读审批。

随后选择有来源的 AuditQuestion，再决定继续、解释、暂停、分出局部问题或形成义务。正式问题引用地图版本、相关 Activity、实际 Behavior、一个 principal Fact 及 lifecycle，并说明上下文、路径和选题理由；单题不必同时覆盖 A1/A2。共享 Behavior、Fact 及相同 lifecycle/context 可以服务不同判别，不归单个 Candidate 所有；独立后续无需挂到旧题下。父问题的反证和未知不会随子问题检查完成而消失。普通细节未知、未映射 Surface 和前置探索均可保留；解释性结论不是执行 Evidence。

提交入口按产物区分，完整字段以运行目录中的 schema 为准：

| 产物 | 作用与继续方式 |
| --- | --- |
| `continue/pause/explained/obligation` | 保存当前完整问题；义务可先于测试受理。`candidate_id` 续写，`parent_candidate_id` 分出不同问题。 |
| `check/revise_check` | 为已有 `unit_id` 提交计划和独立 harness，可携带固定辅助文件；也支持同次提交一个新义务。普通编译、fixture 或未触达修复无需 checker issue。 |
| `model` | 分别提交元数据、Behavior、Properties。可归属 Candidate/Surface 或已受理 Unit；核心完成的 ModelDraft 做 SANY/TLC，F1 与编码修订保留前版。实现见证另走 check，不再自动装配 Bundle／实验／校准／重放归因链。 |
| `research` | 保存部分 AuditSpec、增量关系图或来源化 ScopeUpdate；地图可与一个图操作同次提交，新背景代码不计作已检查义务。 |
| `semantic_revision` | 通过已有 F2/F3 校验修改语义或扩展依赖范围，明确声明改动并保存历史。 |
| `review` | 使用 `review_contract.py` 的实际要求复核制品。复核栏目与被挑战组件分开；输入修复保留 oracle，编码修复改变相应观测或判据，均需新制品、新执行及针对原 issue 的回答。纯补源可解决同版本争议。 |
| `explore` | 无义务时也可提交隔离探索程序，保留日志，但不生成性质证据。 |
| `stop` | 区分 Candidate、问题家族、配置重点和本次运行；记录理由与相关对象。剩余工作从状态派生，局部 checked 不代表重点已穷尽。 |

Candidate 可携带完整地图文件，合并 check 也复用这一入口：来源、地图、问题、义务与绑定、制品依次校验，通过后一次受理并执行。首个义务前可用有来源的 feedback.answered 收敛当前问题，原问题保存在 history；无需 F2 或单独审批调用。已有义务后的规范或范围变化仍走 F2/F3。任何部分无效，本次新增对象均不受理；此前独立受理的义务保留。所有可执行 Unit 必须接到已有 Candidate，包括 graph/scope/F2 入口。

地图更新按对象 ID 比较完整差异；修改或删除旧对象必须声明来源、理由和影响类型，空更新不产生版本。无关 Surface 或独立消费者的添加不重跑旧检查；新 producer／失效路径须解释对当前见证的影响，不能统一当作背景。地图与组合提交都填写当前基准版本，由控制器归一化结果版本和反向索引。共享对象增补用一份 `preserves` 说明旧命题为何仍适用；`challenges` 按 Candidate 指出受到挑战的具体前提。新地图与待核实的 ReviewIssue 同事务受理，原执行保留，相关当前归因不再无条件确认。当前地图可为 v3，而未受影响的检查继续按 v1 解释，不消耗修订或重执行额度。规范适用含义、故障或配置范围变化走 F2，保留命题的依赖展开走 ScopeUpdate/F3；纠正 Fact 的实现认识不自动等于改规范。已解释或已关闭问题也可被具体新来源挑战，再通过现有 review 的 applicability 回答。来源化说明仍可被质疑，不是自动证明。

解释、暂停或检查复核后的下一决定，用 `feedback` 关联实际结果、已回答判别、剩余问题及理解变化。可单独提交 `research`，也可与地图等产品合并；独立交接可早于 Candidate／可用概览，不增加地图版本或 Evidence。引用必须属于本次运行的来源或保留执行。控制器派生当前提交是否改地图；`understanding` 若填写，表达此前研究对理解的影响。`question_updates` 显式按 Candidate ID 更新当前未知与恢复条件，需 `answered` 和有来源的引用；保留旧问题、反证和反馈历史，不通过关键词自动清空未知。实际执行进度从 CheckRun 派生；切换选题不再把“尚未执行”等旧未知机械抄成恢复条件。无关历史反馈不阻塞当前检查。待办和版本由控制器派生，不要求复制精确集合。

调查暂停表示当前让位，实际结果按关联要求和检查投影；自动切换不生成重做已完成检查的恢复任务。Candidate／family 处置只影响显式列出的 Candidate，不按 Fact／context 元组或父子关系扩散；focus 的局部退出返回同一审计入口。未受理地图／问题用既有 operation 归档和 `repair_of` 串联，不制造已受理 Candidate。独立诊断改变会记录为修复进展，同一诊断反复出现可暂停该草稿，保留原稿、pending Unit 和 issue，不终止其他调查。

正常 run／focus 停止用 `frontier_comparison` 列出相关对象、下一步、当前是否可推进及理由，可合并有共同理由的方向。整轮停止须覆盖已记录待办、暂停问题和未展开 Surface，以及非定向运行尚未完成的核心概览；任一步仍可推进即退回，同一规则适用于完成、依据不足和无可行方向三种原因。局部结果不能支持更广后果、待办列表为空、需要另起选题，都不能单独支持整轮停止。Codex 依据剩余时间、调用和权限判断调查价值，控制器检查引用与决策一致性，不另设选题器；可合理提前结束，不强制穷尽未知或预算。用户停止、全局资源耗尽或权限／认证障碍可靠终止；这类强制退出即使元数据无效也保存原稿和诊断，不应用附带语义修改。

`research.json` 始终是工作索引：详细保留当前问题、待执行责任与开放争议，其他问题、结果和所有受理交接保留短入口。旧交接不会因新交接出现而丢失定位，也不会按相同引用合并。checkpoint 在预留调用额度后按同一规则更新索引；prompt 只指向它，报告在内存中展开完整详情。mapped 表示已有描述；出现过 A1/A2 标签或检查过一个 Unit 不表示该区域穷尽。按逻辑义务归并当前制品版本，分别表达核心安全性、有界活性或相关实现语义，以及范围内确认／有限未见违反／调查线索。已确认命题直接展示为已确认，条件和补充说明放入详情，真实未决争议明确显示；独立后果作为可选研究方向。

## 执行、修复与恢复

要求及规范适用性完整保存在 Claim／Scope；Harness 说明本次前史、允许故障、调用、保护机制处理与观察方法；Monitor 说明事件身份、前提和独立比较。复用已有 ID，并用简短而实质的 derivation／applicability 解释局部对应，不复制整份 grounding，也不接受空说明或“同上”。新假设、保护路径的省略和 oracle 改变仍走原有声明、复核和必要修订。

原始提交在 JSON 解析前保存。先拒绝草稿路径逃逸和 symlink，再读取并保存所引用文件的固定字节。正式 runner 从这些字节和干净源码副本装配；后续编辑草稿不影响已受理输入，辅助文件不能覆盖目标代码或依赖定义。无效提交不修改已接受研究；已受理后的执行失败单独记录，不伪装成提交被拒。

模型搜索、实际程序执行、轨迹校准和归因是不同结果。正式执行之后刷新 Unit 的检查记录与未完成义务；多个独立场景不能被最后一个成功场景覆盖。复核可改变当前解释，但原始日志、失败版本和旧判据仍保留。必要条件按实际成功事件约束合格性，不把缺少成功当成已经观察到一条成功路径。

直接检查显式指定 `EventMonitor.admission_alias`，指向该操作准入的前提事件；准入、其他前提、结果及适用性分别匹配。结果适用条件不用于过滤准入，即使二者字段同名、值不同。无依赖前提的声明顺序不改变判定；真实因果依赖通过 alias 引用表达。缺少完成、空轨迹或工具超时不能得到 holds，也不能单独宣称一般活性违反。

`revision_needed` 标明被挑战组件，复核栏目不代替修复权限。普通驱动修订通过 `previous_check_id` 和 `repair_issue_ids` 定位旧版本与具体问题；新 Harness legality 说明当前入口、前提与来源，删除的 conflict 必须对应所引 issue 的原始条件。其余要求、oracle、身份与前提关系保持，受理不代表解释已被接受。正式执行后，用现有 resolution 回答 issue；有条件记录时按 `condition_id` 提交来源化处置。未回答的反证和当前版本缺失的对应性复核分别显示，不能靠 PASS 或新版本清空。

静态 conflicts 不再另行拼成永久 blocker；原文留在固定 Claim／Plan，当前效力沿同一 issue／resolution 链查询。新驱动上的回答不会洗白旧执行，只针对某个驱动的争议也不因 checker 同名传播。共享要求的争议影响实际依赖它的检查。来源解释可处理同版争议；明确要求组件修复时，需新输入与实际执行，或额外来源证明原修复判断无需改变输入。规范与故障／配置适用性变化走 F2，保留命题的依赖展开走 F3；改 oracle 或身份／观察编码仍走显式编码修订。

CLI 调用结果、完整原稿、受理事务和正式操作身份分别持久化。恢复先处理已保存回执和已受理执行，再考虑新模型调用；模型调用额度为零不会丢掉这部分工作。已有可靠完成回执不重复执行；没有可靠结果的中断记录为未知，并在剩余工具预算内使用新副本。恢复不重置已用预算，工具版本变化仍要求新运行。会话明确丢失时保留中断记录，从保存的研究继续新会话；认证和额度错误停止模型工作。

`agent_calls` 是 CLI turn 数；内部工具数按完成事件中的唯一工具 item 计数，usage 有则原样保存。`agent_turn_timeout`、`action_timeout`、`total_seconds` 分别限制单次Codex 调查、正式动作和整次运行。正式实验、模型工具、修订和复核仍受工具额度限制；实际生效的总时间／turn／动作超时分别记录。当前剩余能力从配置和 usage 派生，没有执行能力时拒绝新的占位 Unit，但仍可做有预算的源码调查。总时间到期后，已受理未执行的制品保持精确恢复位置，不暗中执行。退稿调用耗时与正式执行耗时分开，退稿不全是浪费。旧材料字符、packet 与 breadth/depth 配额已删除，不能据调用次数或字符数推算 token 或费用。

## 验证和兼容边界

框架 revision 与实际加载清单由 `resources/task-skills.json` 唯一确定，默认加载共识分析、证据审阅和 audit 产品合同；模型方法仅在配置 verifier 时加入。Engine 的 start/resume 均进入 `workflow.audit.execute`，产品通过 `AuditSubmission` 受理；同 revision 的恢复保留会话、操作身份和计数。旧 revision 在 typed state 加载前被拒绝直接恢复，仅输出已保存报告；历史目录、字段和原始日志不迁移，不提供旧名称别名或双写。`validate --run <当前目录> --submission <相对 draft 的产品路径>` 复用正式受理的读取与准备函数，只在内存副本校验；不拿运行锁、不写正式状态、不调用模型或目标。Agent 使用研究索引中的实际 `validation.command`，无需预检票据；正式提交重新固定字节和核验状态。安全路径错误立即拒绝，可独立检查的机械诊断集中返回。

脚本化产品配合隔离的小型目标执行，可验证受理、恢复和事件判定，但不构成真实 Agent 建模或自主发现的证据。真实目标实验与模型检查应分别记录实际执行和适用边界。

真实效果需分别授权，新自主运行使用空研究状态及 `directed_question: null`，不导入旧运行答案。`target.variant: hashicorp_raft` 只标识目标；只有显式 `execution_backend: hashicorp_raft` 才由专用后端提供 `assurance_support_test.go`，通用 `go_module` 不自动注入。该可选 helper 使用真实 BootstrapCluster／NewRaft，接受成员角色和 FSM，控制实际 RPC 请求／回复交付并记录消息及清理；成员资格与交付控制是正常测试辅助，不预制缺陷、断言、最终消费或完整崩溃重启。高层操作仍需独立关联。可用支持文件、Agent 实际读取和固定制品实际包含的支持是不同事实，按对应记录确认。本轮保留默认通用后端和 opt-in helper，不扩建它们。

报告按调查问题（Candidate）、正确性要求（Obligation）、检查制品（Check）及实际归因（Evidence）区分职责，先列运行状态和逻辑义务结果，再列双主线理解、地图变化、当前待办与历史交接、原始日志。历史检查通过制品的 `graph_versions` 和 `basis` 定位原要求／Unit；已变更对象从现有 `graph_history` 按种类、ID、版本读取，不用当前同 ID 对象替代。历史检查链接其原地图版本；Claim 的 pending／unresolved 标为提出时信息，当前待办由执行和复核派生。`research.json` 从权威状态重建，不读回旧投影；`capacity` 是唯一当前预算入口，记录生成时的 elapsed。历史交接文字不覆盖实际执行状态。新 run 默认保留 `research.json`、`state.json`、版本化地图和正式输入／日志，不再重复导出根目录的地图、材料、图、进度、计划五份视图。需要这些副本时运行 `consensus-assurance report --run <目录> --export-views`；此选项不执行目标或调用 Agent，历史 run 仍按实际方法版本只读。
