## 事务、版本与复杂度

合并提交仍复用已有事务副本和 operation ID。地图文件在所有语义对象与计划校验通过后才作为接受版本写入；来源、Candidate、claim、Unit 和制品由同一个图事务采用。完整原稿与输入副本先行保存，失败不留下本次新受理对象；先前独立受理的义务不受后续坏计划影响。`selections.accepted_versions` 记录同次操作的对象版本，实际执行仍另有可靠回执与预算计数。

地图全局版本不直接使所有检查失效。控制器比较相关对象和 producer/consumer 路径；无关添加保留旧依据。相关 Fact 意义变化需要实际 F2 和显式 Unit/question 接回，依赖扩展需 ScopeUpdate/F3；删除旧 ID 或引用旧地图不能绕过。共享 Fact 的多个已有 Candidate 可在同一地图提交中通过 `reconnect_questions` 接回，保留状态与历史，不能借此更改已受理 Unit 的规范含义。

一个 Candidate 只保留一个当前 Unit；局部 scope 前版保留为 revised，独立检查/模型场景在同一 Unit 内分别计数，不用复制相同义务。不同判别仍用不同 Candidate 或有明确结果影响的 child。普通 Candidate 处置可以更新反证/未知的来源化解释，Unit 的原判别和范围保持不变。

新增 `workflow/research.py` 只集中派生索引、待办、反馈引用与停止校验，复用既有 `selections`；没有工具调度、读包池、评分器、动作队列或第二份 Evidence。报告和原生索引复用同一解释。中断原因单独留在 `run_stop`，避免向待恢复的语义事务插入新的决定而破坏幂等。
