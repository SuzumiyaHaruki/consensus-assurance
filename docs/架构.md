# 架构

系统只有一条实现驱动的 CFT 审计路线：源码 → ConsensusAuditSpec → 选定 Fact 生命周期问题 → Goal/Obligation/Binding/AuditUnit → 源码核对、直接执行、受控调度或局部模型 → Evidence → 重新评估整体规格。

`core` 保存类型与端口；`workflow` 依赖类型及端口，在入口组装 agent、源码适配器、执行器和 TLC。目标仓库只读，执行发生在隔离副本。agent 返回结构化建议，实际工具执行、制品关联、来源和证据判定由控制器管理。

整体实现理解使用一个 `ConsensusAuditSpec`：target_profile、恰好七类 activities、behaviors、facts、handoffs、unclassified、coverage_summary 和版本。完整规格写入 `audit-spec/vN.json`；state 仅保存路径/版本；`audit-spec.json` 是当前视图。旧版本与原始回复保留。规格不承载另一套性质图。

Activity 是并列责任坐标，Behavior 是一个触发下的局部语义处理，Fact 是下游可以依赖的语义信息。分支、合并、重试、环和多对多关系都允许。规范性义务仍留在原图；AuditQuestion 只引用规格 ID。描述性修订不能偷偷修改已接受的义务或当前选中事实的语义。

旧 Responsibility、ResponsibilityHandoff、CoveragePoint 及其 backlog/coverage_intent 已由规格和问题引用替代。模型触达引用 Behavior/Fact/Handoff，保留同一历史中的事件序列和身份关联；单点可达不等于交互可达。

`resources/system.md` 放全局运行约束，`resources/skills` 放方法，`resources/tasks` 放薄任务契约。`task-skills.json` 是实际正文装载清单。语义复核输出只保留目标、层面、状态、来源、推导、反证与限制；缺失实质性层面保存已有结果并安排一次聚焦补查。

Graph、ScopeUpdate、ModelDraft/Bundle、F1–F4、真实执行、校准、搜索身份与证据边界沿用现有实现。不同阶段的成功不得互相冒充：schema 合法不等于语义成立，TLC 反例不等于实现缺陷，有限通过不等于整个活动正确。
