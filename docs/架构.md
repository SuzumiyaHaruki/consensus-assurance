# 实现与验证架构

一条流程：描述性 discovery → 对象级 spec_refine → bounded derive → source/direct/schedule/TLC → Evidence → 有界结论 → 回填理解。

核心方法类型是 Activity、Behavior、Fact、Obligation、AuditQuestion、Evidence。内部 Claim 保留义务和假设的存储表示；不存在 Goal kind、goal_ids 或独立 Handoff 类型。多参与者后果观察使用 ConsequenceObservation，复用原有身份、事件及来源关联检查；不存在并行的 Goal 观察路径。

ConsensusAuditSpec 的字段为 version、target_profile、activities、behaviors、facts、surfaces。Behavior 的 produces_fact_ids/consumes_fact_ids 唯一声明事实关系；Activity.behavior_ids、Fact.established_by/consumed_by 是派生索引。完整受理版本在 audit-spec/vN.json，当前路径和版本在 state；未受理草稿单独归档。

字段级 OutputRepair 处理格式、枚举、来源和定位。SpecIssue 聚合描述不一致，按关联对象分组，进入现有 spec_refine。每组已有来源首次即附带；完整候选重验后才受理。已被问题使用的事实含义、身份和有效上下文变化仍需 F2，不能借描述重整偷换检查义务。

derive 只选一个主要事实生命周期，产生一个主要义务及最小代码绑定、关系和问题。相关义务可以是依赖，不扩大同时检查的性质集合。可靠局部执行优先于普通理解缺口。audit-progress.json 只是调度支持视图，不能充当审计完成证明。

核心与工作流依赖领域类型及端口。插件仍在入口组装；直接执行隔离、源码快照、独立 oracle、关联前史、TLC、校准、回放和 F1–F4 的证据边界保持。实际源码决定行为，义务决定检查器，工具输出与适用性决定证据层级。

当前版本 obligation-audit-v1。旧状态仅通过 history/offline 适配后查看；运行恢复要求版本一致，不把旧图按新语义续跑。
