## 失败链条

1. **复核引用与实际上下文被混为一谈。** `R_apply_commit` 的后续复核引用了新取得的 leader/FSM 材料，但解决回复没有再次列全旧 issue 的来源。`reviews.validate_resolutions()` 将引用集合不包含旧来源报成“实际复核上下文缺少证据”，尽管这些来源已在原任务包中。后续修复包优先填入旧诊断材料，在 16,000 字符错误上下文限额内遗漏了当前需要的多段代码。四次修复均请求已缓存片段，原候选未形成有效修改，修复会话最终耗尽次数。缺少引用与缺少实际发送材料应分别诊断；不能靠框架自动宣告争议解决。
2. **定位修正尚未接上有依据的范围修订。** commitment 建模请求实际取得 `util.go` 和 `configuration.go`。新增图提案同时存在两项声明身份诊断、三项单元用途诊断：部分绑定范围跨越多个声明，input/environment 用途又缺少明确选定的支撑链。修复只把 Configuration 绑定起点改到其声明行，被判定可能删去原行为范围，要求 scope plan。该保护有必要，但本次流程没有完成拆分绑定、明确用途或受控范围修订，不能靠任意缩短范围放行。实际接受的 ScopeUpdate 为 0。
3. **耗尽的是补读次数，不能笼统说材料字符不足。** 六次 targeted read 中，两次取得实际新增依赖，四次只复用缓存。最终唯一材料为 102,037/120,000 字符，仍余 17,963；snapshot 建模所请求的三段合法材料需新增 8,312 字符，本可容纳，却因 `targeted_reads: 6` 已用完未执行。之后三次广度探索均实际发送，仍请求进一步阅读并受同一次数限制。与上一轮不同，本次所有实际发送包都未超过 180,000 字符，不能套用旧的“未发送却扣探索轮数”解释。
4. **语义问题的解释和剩余条件仍需更细区分。** 初始 `U_commit` 的问题将 match 更新和 voter-map 替换一起表述为进度不得下降，宽于 `O_commit` 对 match 报告的单调要求。复核提出仅调整问题表述，但其依据同时记录对旧表述的冲突及其他未决条件，F2 仍保持 unresolved。不能把冲突一律删除来采纳，也不应将“反对旧解释”与“新解释本身无依据”混为一谈。本次目标和义务均保留原版本。

## 对实验反映问题的概括

本次真实实验已经能够从仓库形成有依据的候选目标和局部问题，但“取得依赖材料—补齐关联—修订范围—继续建模”的衔接仍不稳定。16 次 agent 调用中，一部分消耗在复核引用与上下文不一致造成的重复补读；这些缓存读取耗尽了补读次数，使字符额度足够的后续依赖也无法取得。另一条建模路径则停在跨声明绑定及代码用途的受控修正上。结果是两个建模请求均未产出模型，尚无 TLC 性质证据。因此，本次暴露的是框架的修复上下文、预算口径和范围转移问题，不能据此判断 Raft 存在缺陷，也不能用候选数量或耗时代表审计覆盖深度。后续应优先用原回复回归打通上述转移，而非简单扩大额度或放松语义校验。
