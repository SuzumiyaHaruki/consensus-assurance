## 修改与边界

删除 `direct_changes`、`repair_changes`、组件枚举及 `challenged_components`、`out_of_scope_checker_ids`、来源集合新颖性判断和专门的多余 checker 删除许可。正确 oracle 不再为“碰过每个组件”而重写；同一份来源也可以纠正旧复核。普通后继仍保存真实输入差异，并要求自己的执行、观测和复核。

删除 `repair_policy.py`、`ConditionDisposition` 和重复的 `condition_dispositions`／`residual_issue_ids`／`scope_limitations` 处置表，删除未使用的 `parent_issue_id` 和通用图对象复核入口。当前公开复核对象只有 Candidate 和固定检查；图对象仍参与真实依赖及来源闭包。没有保留可选的组件诊断字段。`ReviewIssue.conditions` 继续保存条件 ID、原对象／版本和来源，供条件继承、争议原因和原始记录读取；不要求再抄一份处置理由。同文异主的条件不自动合并。

原 `evidence_ids` 会接受包括 Agent 回合、其他复核和制品在内的已存在 ID；它们不一定是执行证据。现在 `IssueResolution.executions` 直接将实际目标 CheckRun ID 映射到决定性的零基解析事件索引，固定制品随 CheckRun 定位。检查快照、当前输入版本、归属／依赖／显式交接关联、解析和前提；不同探测可以贡献证据，但共同历史兼容性仍需实质解释。Candidate 可以引用自己 Unit 的执行，不必另写关联交接。源码解释型纠正可省略执行引用。非零退出仍只适用既有狭窄见证归因，构建失败、超时、取消等不能充当成功观察。

方法区分条件观测、独立适用的局部合同违反和可达协议违反。优先复用实际初始化、生产者及小规模受控调度；允许局部探测，保留它供给的前提。必要的生产者／共同前史缺口不能仅因终点“局部”而转成独立范围。规范合同、执行历史、当前缺失前提、独立扩展和下一判别条件各用已有对象承载，不增加每轮清单或分类状态。

继续摘要在复核／反馈后仍定位已有执行，并呈现当前 issue 与 Candidate 未知；完整细节按原记录查阅。紧凑视图只补当前未知，不重新塞入旧构造说明。报告保留已处置问题仍有的未知，子问题完成不使父问题自动完成。没有新调度器、回放平台或语义文字去重。

v60 历史记录只作开发依据：Dragonboat 的一个 issue 同时登记 observation/oracle；DeepSeek HashiCorp 三项检查各有 claim/harness 两处条件记录。没有用新规则重评或改写这些归档。baseline 生产实现、提示词、配置、能力及测试文件均未改；`runs/`、`baseline/runs/` 和目标仓库未改。旧方法仍先判版本再恢复，CLI 只展示已保存的旧报告。
