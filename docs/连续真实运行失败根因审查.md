# 连续真实运行失败根因审查

## 结论

主要故障发生在**分析输出进入图结构的接口**，尚未进入验证目标实现的阶段。生成端没有明确收到校验端要求的完整引用与关系语义；校验分层又只向修复端暴露了部分问题。在要求一次提交完整图、且单问题一次失败即停止的配置下，多个独立接口错误逐个暴露，导致反复重新运行却始终没有受理候选。

这不是从最新一条报错推断出来的：对 13:04:51、13:11:23、13:20:53、13:29:17、13:37:06 五次保存的候选进行了只读交叉检查。所有历史失败仍然是失败，没有修改候选、原始响应或报告。此前逐次修复符号名、行号、单个上下文缺失，虽修到了真实缺陷，却没有覆盖完整受理链；因此也没有依据建议连续重新运行来验证整体可用性。

## 根因分解

### 1. 字段名字和实际引用空间没有讲清楚

`Grounding.behavior_ids` 和 `expectation_ids` 实际只接受已读取 Material 的 ID。原字段无说明，候选却在五次运行中都生成了 `B1`、`E1` 或类似行为/期望标签。框架并不存在这些节点，也没有规则把它们解析成材料。

这类错误此前位于 `apply_discovery` 后续的 grounding 校验，先被 `require_graph` 的位置或 code_use 错误挡住。即使修掉当时停止原因，仍会遇到下一层失败，且那层往往只有普通 ValueError，没有可操作的修复字段。

### 2. 同样的自然语言词在生成与校验中含义不同

模型把 support 理解为“与问题有关的上下文”。校验中的 support/handoff 则要求从已检查义务出发，沿选中的 boundary/depends_all/conditional_on 边到达生产者义务或绑定，并保留未验证条件。maps 或 supports 等目标关系不是该依赖路径。

最新候选把 BIND2 改为 support、关联 G1、使用 R2；R2 是 O2 → G1 的 maps，因此依然不合法。不能由框架自动改成 direct/input 来通过，也不能因为代码“有关联”就当作已建立生产者保证。

同样，四次运行存在反向的 Obligation → Goal maps 或没有选中可用 Goal → Obligation 边的单元。语义上谈到了系统后果，不等于图接口要求已经成立。

### 3. 初始输出与局部修复的权限不对称

首次发现同时提交职责、目标、义务、grounding、精确绑定、关系、code_uses 和工作集。局部修复必须保留原判断和行为，不能把跨函数范围默默裁成一个函数，也不能改义务来配合绑定。因此“把位置填错了，再靠一个字段修正”常常根本不是合法操作。

前几轮的限定名缺陷、缺少初始声明索引、schema 错误的空上下文，都是这一接口不完整的具体表现。后来的修复包即使有对象，笼统的 code_use 错误也没有说明究竟是关联 ID、来源、角色还是路径条件失败。

### 4. 串行暴露错误与细粒度失败预算共同放大问题

配置是 `repair_attempts=4`、`repeated_error_revisions=1`。这不等于可随意试四次：一个修复仍触发相同问题键，就会停止。此前同样的错误引用在六个对象上重复出现，如果每次只修一个对象，四次总修复也不够。

预算严格是放大因素，不是增加预算的理由。也不能将每次相同问题改名绕过失败次数。需要让首次输出知道接口，并在同一次结构检查中提供完整、可定位的错误；同类引用纠正应在既有单次字段数量上限内一起进行。

### 5. 原测试主要验证保护措施，未验证开放生成的接口完整性

大量回归从已合法的合成图开始，或用知道框架细节的 responder 修一项故意制造的错误。它们能验证来源、归因、恢复与执行保护，却不能证明真实模型从零生成的图能进入受理链。此前用局部测试通过代替这一层的就绪判断，是验证方式上的缺口。

上述缺失规则、空上下文、非法引用、边方向和计数均可从代码及档案直接确认；“更完整的接口会改善真实生成成功率”仍是待验证的推断，没有新的真实对照结果。

## 本轮修改

不新增流程、图节点、领域 enum、冻结契约或 gate，也不增加预算。这里的 graph_contract 是现有校验规则的可读视图，不是新的准入条件。

- 给 Grounding 和 CodeUse 的现有字段补上准确说明。任务包传入由现有校验常量组装的 graph_contract，明确材料 ID、Goal 关系、代码用途及依赖方向；不注入目标仓库的固定答案。
- 将 grounding 检查接入已有图诊断，与后续受理使用同一实现；结构诊断同时暴露缺失 Goal 关系和 code_use 的具体失败原因，避免一个症状遮住后续必然失败。
- 同一批重复 grounding 引用错误在既有 24 个 replacement 上限内合并为一个修复组；不改变总调用或单问题预算。
- 修复组可同时准确定位多个对象的字段，不再把多个索引都重定位到第一个对象。缺少 Goal 关系时可建议有依据的新关系，并经过完整图校验；不自动反转旧边、修改旧关系含义或扩充已检查义务。
- association/material 修复提供相关依赖对象与源码，仍受原整包上限限制；可见对象并不意味着允许修改所有字段。

生成、诊断与拒绝条件共用实际规则。对修改前后的 code_use 谓词离线比较 960 种角色、claim、关系类型、方向、来源与未验证条件组合，接受/拒绝结果一致。

## 验证与限制

新增测试验证一份初始草稿同时存在多处错误引用和缺失 Goal 关系时，能够在原默认 `repair_attempts=4`、`repeated_error_revisions=1` 下，通过三次实际 MockAgent 调用（发现一次、修复两次）完成结构受理；原始失败候选、旧 maps 边、claim 判断和 checked obligations 保留。它证明接口与有限修复路径可执行，**不是自主发现质量或实现正确性的证据**。
